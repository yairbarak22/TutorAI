# 04 — איך מפיצים ומתקינים (ADR-001)

> **סטטוס:** מוצע · **מחליף:** ההמלצה המקורית (Tauri + Python sidecar) ב-[02-architecture.md](02-architecture.md)

## הבעיה

צריך שלושה דברים בבת אחת:

1. **סטודנט למשפטים** יוכל להתחיל לעבוד תוך דקה, בלי טרמינל, בלי Docker ובלי Python.
2. **סטודנט שתורם** יוכל להריץ את הפרויקט, לשנות ולראות תוצאה תוך 5 דקות.
3. **צוות סטודנטים מתנדבים** יוכל לתחזק את המערכת בלי לבזבז חצי מהזמן על אריזה, חתימות קוד ובאגים של מערכות הפעלה.

## למה ההמלצה הקודמת לא טובה

התוכנית הקודמת הייתה Tauri + מנוע Python שנארז כ-sidecar. הבעיה היא לא Tauri, אלא **המנוע ב-Python עם ספריות ML כבדות** (Docling, BGE-M3, faster-whisper):

| בעיה | המשמעות בפועל |
|---|---|
| גודל | Docling וחלק מהאמבדינגס מושכים את PyTorch. התוצאה היא מתקין של 1–2GB. |
| אריזה | PyInstaller עם torch צריך build נפרד לכל מערכת הפעלה וארכיטקטורה (Mac Intel/ARM, Windows, Linux). זה מקור קבוע לבאגים. |
| שתי שפות | React/TS בממשק ו-Python במנוע, עם API ביניהם. תורם חדש צריך להבין את שני העולמות. |
| חתימת קוד | אפליקציית macOS בלי חתימה ו-notarization נחסמת על ידי Gatekeeper, והסטודנט צריך לאשר אותה ידנית בהגדרות המערכת. ב-Windows מופיעה אזהרת SmartScreen. חתימה עולה כסף (Apple Developer: 99$ לשנה) ודורשת מישהו שאחראי עליה. |
| עדכונים | כל תיקון באג מחייב build, release והורדה מחדש. |

## התובנה שמשנה את התמונה

ממילא **צריך מודל שפה חזק** (Claude, Gemini או GPT) כדי לקבל איכות טובה. מודלים מקומיים על לפטופ של סטודנט עוד לא מספיקים לסיכומים, למבחנים ולקוד ווידג'טים באיכות שאנחנו רוצים. ומודלי ה-API של 2026 כבר יודעים לעשות לבד את רוב מה שתכננו לעשות בספריות ML מקומיות:

| משימה | תוכנן מקומית (כבד) | אפשר דרך ה-LLM, או בקלות ב-JS |
|---|---|---|
| קריאת PDF ושקפים עם נוסחאות ותמונות | Docling + PyTorch | ה-LLM קורא PDF ישירות (Claude, Gemini). pdf.js לחילוץ טקסט מהיר. |
| חיפוש בחומרי הקורס | BGE-M3 + LanceDB | קורס טיפוסי (10–30 הרצאות) הוא בערך 100–300K טוקנים. **הקשר ארוך + prompt caching + אינדקס מבני + BM25** עדיפים ופשוטים יותר מ-RAG וקטורי בסדר גודל כזה. |
| תמלול הרצאות בעברית | faster-whisper | API תמלול, או בהמשך מודלי ivrit.ai (יש להם גרסאות ggml ו-ONNX) |
| חזרה מרווחת | py-fsrs | **ts-fsrs**, הספרייה הרשמית של אותו פרויקט |
| אימות מתמטי (SymPy) | Python | **Pyodide** (Python ב-WebAssembly) בתוך Web Worker |

**המסקנה: אפשר לכתוב את כל המערכת ב-TypeScript בלבד.** בלי Python בזמן ריצה ובלי שרת. ברגע שזה נכון, נפתחת אפשרות פשוטה בהרבה.

## ההחלטה

### שכבה 1 (ברירת המחדל): אפליקציית ווב local-first

- **אתר סטטי** (Cloudflare Pages או GitHub Pages). אין שרת ואין מסד נתונים מרכזי.
- **כל הנתונים נשמרים מקומית, ב-SQLite.** ב-Chrome וב-Edge הקובץ נמצא **בתיקייה רגילה שהסטודנט בוחר** (ראו "איפה הנתונים נשמרים" בהמשך). בשאר הדפדפנים הוא נשמר באחסון של הדפדפן (OPFS).
- **קריאות ל-LLM יוצאות ישירות מהדפדפן לספק** עם המפתח של הסטודנט. Anthropic, OpenAI ו-Gemini תומכים בזה. המפתח לא עובר דרכנו.
- **התקנה**: נכנסים לקישור. מי שרוצה לוחץ "התקן אפליקציה" ב-Chrome או Edge, או "Add to Dock" ב-Safari, ומקבל אייקון וחלון משלו.
- **עדכון**: כל merge ל-main מתפרסם אוטומטית ומגיע לכולם בטעינה הבאה.
- **תרומה**: `git clone && pnpm i && pnpm dev`. לכל PR נבנה preview עם קישור משלו, כך שהמבקרים, ואפילו מרצה, יכולים לנסות את הפיצ'ר בלי להתקין כלום.

### שכבה 2 (בהמשך, רק כשיש צורך אמיתי): אפליקציית דסקטופ מאותו קוד

**Electron** שעוטף את **אותו קוד בדיוק** ומחליף רק את "שכבת הפלטפורמה":

- אחסון בתיקייה רגילה על הדיסק (`~/RuecAI/`) במקום בדפדפן
- תמלול מקומי (whisper.cpp עם מודלי ivrit.ai), עבודה מול Ollama, ופלאגינים שדורשים Python (Manim)
- עיבוד ארוך ברקע גם כשהחלון סגור

**למה Electron ולא Tauri?** אם הכול ב-TS, Electron מאפשר לכתוב גם את החלק ה"נייטיבי" ב-TS (Node), בלי Rust. הוא גם מריץ את אותו Chromium בכל מערכת הפעלה, כך שהקוד מתנהג בדיוק כמו בגרסת הווב. Tauri משתמש ב-WebKit ב-Mac וב-WebView2 ב-Windows, ולכן יש הבדלים בין מערכות. הגודל (~100MB) לא משנה לסטודנט. חתימת קוד לגרסה הזו היא הזדמנות טובה לבקש מימון מהאוניברסיטה.

### איך שתי השכבות חולקות קוד

```
packages/core           ← כל הלוגיקה: קורסים, צינורות, כלים, מודל לומד (TS טהור)
packages/platform       ← ממשק: Storage, FileAccess, Transcriber, JobRunner, SecretStore
  ├─ platform-web       ← OPFS + sqlite-wasm + Web Workers + WebGPU
  └─ platform-desktop   ← fs + better-sqlite3 + whisper.cpp + Ollama   (שלב מאוחר)
apps/web                ← React, נפרס כאתר סטטי
apps/desktop            ← Electron, טוען את apps/web + platform-desktop   (שלב מאוחר)
```

פלאגינים כותבים רק מול `core`. הם לא יודעים ולא צריכים לדעת על איזו פלטפורמה הם רצים.

## איפה הנתונים נשמרים: תיקייה מקומית רגילה

ה-DB הוא **קובץ SQLite רגיל בתיקייה על הדיסק**. האתר ניגש אליה דרך File System Access API של הדפדפן. אין שרת מקומי ואין התקנה.

```
~/Documents/RuecAI/                ← הסטודנט בוחר את התיקייה פעם אחת
  ruecai.db                        ← SQLite: קורסים, מושגים, תוצרים, התקדמות, כרטיסיות
  courses/
    probability/
      sources/lecture-01.pdf ...   ← הקבצים המקוריים, כמו שהם
      exports/summary-week3.md     ← תוצרים שיוצאו (Markdown/HTML)
```

**איך זה עובד טכנית:**
- SQLite-WASM רץ בזיכרון בתוך Web Worker. כל שינוי נכתב לקובץ `ruecai.db` בתיקייה, עם השהיה קצרה (debounce) וכתיבה אטומית (קודם לקובץ זמני, ואז החלפה). ה-DB קטן, כמה MB, כי הקבצים הכבדים נשמרים בנפרד.
- הקבצים המקוריים נשמרים כקבצים רגילים, והסטודנט רואה אותם בתיקייה.
- **שכבת הפלטפורמה זהה לזו של Electron:** `platform-web` כותב לתיקייה דרך הדפדפן, ו-`platform-desktop` כותב לאותה תיקייה דרך Node. **אותה תיקייה ואותו פורמט.** אפשר לעבור בין האתר לאפליקציה בלי מיגרציה.

**היתרונות:**
- ניקוי נתוני גלישה לא מוחק כלום.
- גיבוי = העתקת תיקייה.
- **סנכרון וגיבוי בחינם:** אם התיקייה נמצאת בתוך Google Drive, OneDrive או Dropbox, הנתונים מגובים ועוברים בין מחשבים (בתנאי שעובדים על מחשב אחד בכל פעם; יש נעילה פשוטה בקובץ `.lock`).
- שקיפות: הסטודנט רואה בדיוק מה נשמר.

**המגבלות:**
- **נתמך רק ב-Chrome, Edge ושאר הדפדפנים מבוססי Chromium.** Safari ו-Firefox הודיעו שלא יממשו את ה-API. בהם המערכת עובדת עם OPFS, גיבוי אוטומטי לקובץ `.ruecai` ואזהרה. ההמלצה הרשמית לסטודנטים תהיה Chrome או Edge.
- הדפדפן מבקש אישור גישה לתיקייה. בגרסאות עדכניות של Chrome יש אפשרות לאשר לצמיתות, ואחרת זה קליק אחד בפתיחה.

**חלופה שנבחנה ונדחתה: "שרת DB מקומי קטן"** (תוכנה קטנה שמריצה SQLite ו-HTTP על localhost, והאתר מתחבר אליה). זה מחזיר את כל בעיות ההתקנה: הורדה, חתימת קוד, עדכונים, אנטי-וירוס ופורט תפוס. בנוסף, דפדפנים מוסיפים הרשאות וחסימות לגישה מאתר ל-localhost. אין לזה יתרון על פני גישה ישירה לתיקייה, ואם בכל זאת צריך תהליך מקומי, Electron בשלב 4 עושה את זה טוב יותר.

## הסיכונים של local-first בדפדפן, ואיך מתמודדים איתם

| סיכון | מענה |
|---|---|
| הסטודנט מוחק נתוני גלישה ומאבד הכול | ב-Chrome/Edge **זה לא קורה**: הנתונים בתיקייה רגילה. ב-Safari/Firefox: `navigator.storage.persist()` וגיבוי אוטומטי לקובץ `.ruecai` (ZIP). |
| Safari מוחק אחסון של אתרים שלא בשימוש 7 ימים | הכלל חל על אתר שנפתח ב-Safari, ואפליקציה שנוספה ל-Dock או למסך הבית מקבלת מונה משלה. לכן: להמליץ ל-Mac ב-Chrome או Edge, או על "Add to Dock". להציג אזהרה ב-Safari. **צריך לבדוק התנהגות OPFS בפועל על Safari עדכני** (לא מתועד בבירור). |
| עבודה ארוכה (תמלול, לומדה שלמה) נעצרת כשסוגרים את הטאב | עבודה בשלבים שנשמרים (checkpoints) וממשיכים בפתיחה הבאה. התראה "אל תסגור". זו גם הסיבה העיקרית לשכבה 2. |
| מפתח API שמור בדפדפן | זה המפתח של הסטודנט, ונשאר אצלו. נשמר מוצפן ב-IndexedDB, עם אזהרה לא להשתמש במחשב משותף. ב-Electron: keychain של מערכת ההפעלה. |
| קוד שה-LLM מייצר (ווידג'טים) רץ בדפדפן | iframe עם `sandbox` בלי `allow-same-origin`, ו-CSP שחוסם רשת. הקוד לא יכול לגשת לנתונים או למפתח. |
| אין RAG וקטורי | בקורס בגודל רגיל הקשר ארוך עובד טוב יותר. אם יתברר שצריך, מוסיפים אמבדינגס בדפדפן (transformers.js) או דרך API, מאחורי אותו ממשק `retrieve()`. |
| האוניברסיטה רוצה לספק מפתח מרכזי | Cloudflare Worker דק (proxy) עם התחברות אוניברסיטאית ומכסות. זו התוספת היחידה בצד שרת, והיא אופציונלית. |

## מה הסטודנט חווה בפועל

1. נכנס ל-`ruecai.app` (לדוגמה) ← "התקן" (לא חובה)
2. מדביק מפתח API (או מתחבר עם חשבון אוניברסיטה, אם יהיה proxy)
3. "קורס חדש: הסתברות" ← גורר 12 קבצי PDF
4. תוך דקה-שתיים מקבל מפת נושאים, ומשם: סיכום, טוטור, חידון, ווידג'טים

**אפס התקנות. אפס עדכונים ידניים. אפס עלות תפעול לפרויקט.**
